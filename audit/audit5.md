# Пятый аудит Unbihex: производительность

- **Дата:** 2026-10-29
- **Что проверялось:** `origin/main` `27e3905`, рабочее дерево без локальных правок.
- **Что именно:** горячие пути данных и установления соединения — TUN и userspace-стек (ipstack), DNS, relay, outbound-протоколы (VLESS/Vision/REALITY/Shadowsocks/XHTTP), маршрутизация, server-режим, клиентское ядро.
- **Метод:**
  - статический разбор всех горячих путей плюс исходников зависимостей `ipstack 1.0.1` и `tun-rs 2.8.13`;
  - release-сборка и микробенчмарки на этой машине (16 ядер, Rust 1.99.1);
  - сравнение сборки с `lto=fat` / `codegen-units=1` / `panic=abort`;
  - живых замеров через WAN и профилировщика **не было** — все цифры либо локальные микробенчмарки, либо расчёт и помечены как «оценка».
- **Предыдущие аудиты** (audit.md…audit4.md) — про безопасность и задержку REALITY; здесь только производительность.

## Итог

Четыре находки в коде дают почти весь эффект; пятая нашлась на сравнительном стенде:

1. **Окна TCP в TUN-стеке оставлены по умолчанию — 16 КБ** (`tun.rs:260-262`). Это жёсткий потолок `16 КБ / RTT` на каждое TCP-соединение в обе стороны: 6.5 Мбит/с при RTT 20 мс, **1.3 Мбит/с при 100 мс**, 0.65 Мбит/с при 200 мс. Правка — три строки.
2. **`TunIo::poll_read` возвращает EOF как `Ok(())`, а ipstack ждёт `Ok(n)`** (`tun.rs:129`, `ipstack/src/lib.rs:320`). После любого сбоя чтения TUN стек уходит в **busy-loop на 100 % ядра** и не останавливается.
3. **DNS в TUN без кеша ответов**, с новым UDP-сокетом и 64-КБ буфером на каждый запрос (`dns/server.rs:136`, `dns/client.rs:120`), и последовательной обработкой на поток (`tun.rs:425`): каждый запрос — ~5–10 мкс плюс RTT, медленный запрос блокирует следующие на том же сокете.
4. **Периодические аллокации на каждый пакет** в TUN-петле (3–4 `Vec` на round-trip, `tun.rs:205,141`) и в UDP-протоколах (`shadowsocks.rs:510`, `vless.rs:461`), плюс MSS не объявляется — приложение шлёт по 536 Б вместо ~1360 Б (`tun.rs:260`).

Отдельно, на стенде сравнения (см. [`compare.md`](compare.md)), измерена пятая находка: **в proxy-режиме клиент упирается в окно приёма TCP ~50 КБ** и на RTT 50 мс даёт 0.9–1.5 МБ/с на поток против 89–101 МБ/с у Xray и sing-box. Тот же клиент без правок кода даёт 108 МБ/с, если поднять `net.ipv4.tcp_rmem`; значит, автотюнинг окна не срабатывает и это лечится явным `SO_RCVBUF` в `net/socket.rs` (п. 2.6).

## 1. Критично

### 1.1. Окна TCP в TUN: 16 КБ вместо 256 КБ

`tun.rs:260-262` переопределяет у `TcpConfig` только `timeout`; `read_buffer_size` и `max_unacked_bytes` остаются дефолтными `16 * 1024` (`ipstack/src/stream/tcb.rs:5-6`).

Как это работает в ipstack:
- входящее окно, которое объявляется пиру, — `get_available_read_buffer_size()` = `read_buffer_size` минус несобранные пакеты (`tcb.rs:126`, `tcb.rs:200`);
- исходящее — `is_send_buffer_full()` = `max_unacked_bytes.min(remote_window)` (`tcb.rs:320-324`).

Итог: **не более 16 КБ в полёте на соединение в каждую сторону**. При RTT 100 мс это 1.3 Мбит/с на поток, сколько бы ни давал канал; для браузера с 6–8 потоками — 8–10 Мбит/с. Это же объясняет «медленно на длинных плечах, нормально на ближних».

```rust
// tun.rs:260
let mut tcp_cfg = TcpConfig::default();
tcp_cfg.timeout = tcp_idle;
tcp_cfg.read_buffer_size = 256 * 1024;    // окно приёма
tcp_cfg.max_unacked_bytes = 256 * 1024;   // окно отправки
tcp_cfg.options = Some(vec![TcpOptions::MaximumSegmentSize(cfg.mtu - 40)]);
```

Память почти не растёт: буфер ipstack — это счётчик и `BTreeMap` несобранных пакетов, реальные байты выделяются только под пришедшие данные. `TcpOptions` экспортируется из `ipstack` (`lib.rs:23`).

### 1.2. EOF TUN-устройства превращается в busy-loop

```rust
// tun.rs:129
Poll::Ready(None) => Poll::Ready(Ok(())),
```
Для `AsyncRead` это «0 байт = EOF», но ipstack читает так:
```rust
// ipstack/src/lib.rs:320-322
select! {
    Ok(n) = device.read(&mut buffer) => { ... }
```
`Ok(())` всегда готов, значит `select!` крутится без ожидания и без сна. Срабатывает после любого `tracing::error!("tun read: {e}")`: reader-таск выходит (`tun.rs:196-200`), канал закрывается, `poll_recv` отдаёт `None` — и ядро занято навсегда, при этом `cancel` никто не взводит.

```rust
Poll::Ready(None) => Poll::Ready(Err(std::io::ErrorKind::BrokenPipe.into())),
```
и в reader-таске на ошибке `device.recv` добавить `cancel.cancel()`.

## 2. Высоко

### 2.1. Не объявляется MSS

`TcpConfig.options` = `None`, `TcpOptions` в коде движка не используется нигде (grep). `write_packet_to_device` передаёт `config.options.as_ref()` (`ipstack/src/stream/tcp.rs:528`), то есть SYN-ACK уходит без опции MSS. По RFC 879 приложение внутри TUN считает MSS = 536 Б: **в 2.5 раза больше пакетов** на каждый байт от приложения, соответственно больше работы стеку, маршрутизатору, шифру и pps-нагрузки на всё остальное. Фикс — строка из 1.1.

### 2.2. Четыре аллокации и три копии на пакет в TUN-петле

| Место | Что |
|---|---|
| `tun.rs:205` | `in_tx.try_send(buf[..n].to_vec())` — аллокация на RX-пакет |
| `ipstack packet.rs:70,114-129` | `put_slice` (копия) и `payload.to_vec()` при разборе |
| `tun.rs:141` | `self.tx.try_send(buf.to_vec())` — аллокация на TX-пакет |
| `tun.rs:192` | буфер переиспользуется, это хорошо; но `to_vec` убивает выигрыш |

Оценка: 200–400 нс и ~4 malloc/free на round-trip; при 90 kpps — 2–4 % ядра только на аллокатор, плюс давление на него. Лечится пулом `Vec<u8>` (free-list) между writer/reader и ipstack.

Отдельно: пакетный цикл — один пакет на `recv`/`send`, без батчинга и без GSO/GRO (`tun-rs 2.8.13` умеет `offload(true)` + `recv_multiple`/`send_multiple`, это даёт заявленные 2–10× throughput, но требует разбора `virtio_net_hdr` и сегментации перед ipstack). Минимальный шаг без смены API — дренаж очередей пачками (`try_recv` в цикле + `readable().await`), чтобы на N пакетов приходился один wakeup вместо N.

### 2.3. DNS в TUN: кеша нет, сокет на запрос, 64 КБ буфера, HOL

- `dns/server.rs:136-148`: `handle()` для всего, что не A/AAAA/fake-IP, идёт в `forward()`, кеша ответов нет вообще. `DnsClient.cache` используется только `Resolver::resolve` (свой трафик движка), а `exchange()` кеш не смотрит. Повторяющиеся MX/TXT/SRV/AAAA-запросы всегда бьют в апстрим.
- `dns/client.rs:120-123`: на каждый запрос `udp_bind` + `connect` + `send` + `recv` + закрытие и сразу `vec![0u8; 65_535]` на ответ (измерено 2.8 мкс только на аллокацию). `dns/client.rs:140-146,154-167`: запрос копируется целиком для смены ID, ответ парсится целиком в `Message` ради сравнения вопроса.
- `dns/server.rs:186-206`: routed-запрос (`dns_hijack` + правило `proxy`) открывает **новый outbound-флоу на каждый DNS-запрос**.
- `tun.rs:425-438`: `serve_dns` обрабатывает запросы последовательно на один 5-tuple; forward может занять до 5 с (`ROUTED_TIMEOUT`), и все следующие запросы с этого сокета ждут. Stub-резолвер браузера шлёт в один сокет — «залипание» страницы на секунды.

Минимальный набор: LRU-кеш ответов в `DnsServer` (ключ — wire-qname/qtype/qclass, TTL из ответа, clamp 5…3600 с); буфер 1232 Б вместо 64 КБ; одно connected-соединение на апстрим с мультиплексированием по ID; forwarded-запросы — в отдельную задачу с семафором, чтобы не блокировать поток.

### 2.4. Проверка пользователя хеширует всё дважды на каждого

`inbound/mod.rs:29-43`: `ct_eq` хеширует **обе** стороны (`Sha256::digest(a)`, `Sha256::digest(b)`), а `check_user` вызывает его дважды на пользователя. Итого **4 SHA-256 на пользователя на каждое рукопожатие**, без early-exit. Измерено: 100 юзеров — 181 мкс, 1000 — **1.8 мс** на соединение. Для панелей с тысячами ключей при 100 conn/s это ~18 % ядра.

```rust
struct User { uuid: [u8; 16], name_hash: [u8; 32], pass_hash: [u8; 32], .. }
// на загрузке конфига посчитать один раз; на соединении — 2 хеша входа
let name_h = Sha256::digest(name);
let pass_h = Sha256::digest(pass);
users.iter().fold(false, |ok, u| ok | (ct_slice(&u.name_hash, &name_h) & ct_slice(&u.pass_hash, &pass_h)))
```
Для VLESS (`inbound/vless.rs:394-400`) константное время не нужно: uuid ищется по `HashMap` или по предвычисленному `[u8;32]`.

### 2.5. REALITY-сервер: probe к `dest` на каждое подключение

`inbound/reality.rs:147` вызывает `reality_shape::probe(&self.dest, &prefix)` **на каждое** успешное REALITY-рукопожатие, а `probe` (`reality_shape.rs:58-66`) делает `lookup_host(dest)`, новый TCP-connect, отправку ClientHello в `dest` и паузу `gap` = 2–15 мс. Это же подтверждали audit2–audit4: задержка ServerHello у своего сервера выше, чем у `dest`.

Форма ответа `dest` (группа, suite, длины записей) от коннекта не зависит — её можно кешировать по `(dest, набор групп из ClientHello)` на 5–10 минут, а адрес `dest` резолвить один раз при старте. Это убирает из критического пути RTT до `dest`, `gap`, DNS и удвоенную TLS-нагрузку на `dest`. Дополнительно `reality.rs:278` строит новый `ServerConfig` и новый `CryptoProvider` (ring) на каждое рукопожатие — провайдер стоит кешировать по паре `(group, suite)`.

**Измерено** на стенде `compare.md`: сервер Unbihex даёт TTFB 7.2 мс и 254 соединения/с, Xray с тем же клиентом — 3.0 мс и 544/с; клиент Unbihex против сервера Xray — 3.7 мс. То есть ~4 мс на рукопожатие добавляет именно серверная сторона, и это ровно цена probe + `gap` 2–15 мс.

### 2.6. Клиент в proxy-режиме не растит окно приёма TCP

Измерено на стенде сравнения: при эмуляции RTT 50 мс один поток через Unbihex-клиент даёт **0.92 МБ/с**, тогда как Xray-клиент в тех же условиях — 88.8 МБ/с, sing-box — 101.5 МБ/с. Перекрёстные пары показывают, что виноват клиент: Xray-клиент → Unbihex-сервер держит 88.8 МБ/с.

Причина видна в `ss -tinm` во время передачи: у клиентского сокета `rcv_wnd ≈ 40–55 КБ` (`rcv_space` 38 КБ, буфер `rb87380`), у серверного — `rwnd_limited: 73.8 %` и 11 МБ `notsent`. Это ровно `окно / RTT`. Тот же клиент без изменений в коде даёт **108 МБ/с**, если поднять только `net.ipv4.tcp_rmem` (по умолчанию 87 КБ → 4 МиБ): ядро получает большой буфер, и окно перестаёт быть потолком.

```rust
// net/socket.rs: tcp_connect, после set_tcp_nodelay
let _ = sref.set_recv_buffer_size(4 * 1024 * 1024);
let _ = sref.set_send_buffer_size(4 * 1024 * 1024);
```

Почему автотюнинг не срабатывает у нас, а у Go-клиентов срабатывает — отдельный вопрос (вероятно, из-за чтения ровно по одной TLS-записи: `tls_stream.rs:69-116`, приложение вычитывает буфер быстрее сети, и ядро не видит «давления», при котором растит `rcvbuf`). Явный размер буфера решает задачу независимо от причины; проверить на стенде с реальным RTT.

## 3. Средне

### 3.1. Shadowsocks UDP: 64 КБ на пакет + HKDF + `Box` шифра

`shadowsocks.rs:510`: `let mut pkt = vec![0u8; 65_535];` **на каждую принятую датаграмму** (2.8 мкс). `seal_udp` на каждый отправленный: `random_salt` (Vec) + `derive_subkey` (Vec, HKDF-SHA1, 1.9 мкс) + `AeadCipher::new` (`Box`, 0.23 мкс). Часть цены обязательна по протоколу (соль на датаграмму), но буфер и `Box` — нет: `AeadCipher` держать в структуре и лишь переустанавливать подключ, `pkt` — переиспользовать.

### 3.2. VLESS UDP: мьютекс, аллокация и flush на каждую датаграмму

`outbound/vless.rs:461-471`: `Vec::with_capacity` под кадр, `self.w.lock().await` (tokio-мьютекс), `write_all`, `flush` — на каждый пакет. Датаграмма = отдельная TLS-запись = отдельный `write` syscall. Это фактически запрет батчинга для QUIC: несколько кадров можно собрать в один буфер и писать раз в N мс / при заполнении. `recv` (`vless.rs:477-489`) читает длину и тело двумя `read_exact` — тоже без буферизации.

### 3.3. UDP-путь relay: 64 КБ на направление на флоу

`relay.rs:15,127`: `vec![0u8; 65_535]` на каждое направление каждого UDP-флоу. TUN создаёт флоу на каждый 5-tuple, то есть **~130 КБ на активный UDP-флоу**; сотни флоу — десятки мегабайт. Датаграммы TUN ограничены MTU, хватит 2–4 КБ либо пула 64-КБ буферов.

### 3.4. TLS: чтение ровно одной записи и отключённый resumption

- `tls_stream.rs:69-116`: `Feed::read` читает сначала 5-байтовый заголовок записи отдельным `read`, затем тело; один `poll_read` отдаёт не больше одной записи. Для Vision это нужно (ловля `CMD_DIRECT` на границе записи), но после перехода в обычный режим (`vision.rs:380-381`) и для обычного VLESS без Vision — накладные расходы: +1 syscall на запись. Владелец проекта проверил гипотезу в `bench/ab-test-2026-10-29.md`: чтение крупными кусками не даёт эффекта (TLS-слой и так держит ~10 Гбит/с на поток), правка откачена — пункт снимается.
- `tls.rs:95-103`: при любом fingerprint (по умолчанию Chrome) `resumption` **отключён** — PSK-binder покрывает байты rustls, а rewriter их меняет. Следствие: каждое новое TCP-соединение — полный TLS 1.3 handshake с ML-KEM keygen и проверкой цепочки, без 0-RTT. Для браузера, открывающего соединение на каждый ресурс, это лишний RTT и заметный CPU. Правильное решение — пересчитывать binder в rewriter; дешёвое — оставлять resumption для `fingerprint: "none"`.

### 3.5. Счётчики трафика: false sharing

`stats.rs:8-16`: четыре `AtomicU64` в одной структуре, `fetch_add` на каждый чанк/датаграмму. Замер на 4 потоках: **22.8 нс/оп против 2.0 нс** с `#[repr(align(64))]`. Лечится выравниванием и/или локальным накоплением со сбросом раз в 64 КБ.

### 3.6. Маршрутизация: линейный CIDR и аллокация на матч domain-set

- `router.rs:239`: `self.cidrs.iter().any(|n| n.contains(&ip))` — `Vec<IpNet>`, при этом рядом есть `IpSet` с бинарным поиском (`rules/ipset.rs:48-51`). `try_merge` (`router.rs:207-209`) склеивает подряд идущие CIDR-правила в один длинный `Vec`, так что сгенерированные списки дают O(CIDR) на соединение.
- `rules/succinct.rs:240-242,289`: `reversed(domain)` аллоцирует `String` на каждый матч domain-set (`domain_suffix` в `.srs`/geosite). Нужен обход по обратному итератору байт.
- `dispatcher.rs:272-280`: при direct-маршруте без domain-решения правила прогоняются **заново на каждый resolved IP**. Достаточно один раз выбрать «block/direct/proxy» и не повторять полный скан на адрес.
- `Router::pick` измерен: 125 нс на 200 правил — сам по себе не проблема, проблема в множителях (×IP) и в CIDR-списках.

## 4. Клиент (unbihex-client)

| Место | Проблема |
|---|---|
| `client-core/src/controller.rs:168-280` | `tokio::Mutex` на всё время connect, а внутри — блокирующие `platform::detect_default()`, `is_elevated()`, `apply_routes()` (9–15 процессов `ip`/`netsh`/`route`) и `set_system_proxy()`. Worker рантайма занят 0.5–2 с, `status()` из UI стоит в очереди на том же мьютексе. Всё платформенное — в `spawn_blocking`, мьютекс держать только на запись состояния. |
| `client-core/src/platform/mod.rs:585-597,610` | журнал пишется целиком (`to_vec_pretty` + `create_dir_all` + `fs::write`) на каждый undo-шаг: ~9 записей на один connect. Нужен один flush на операцию. |
| `client-core/src/ping.rs:98-99` | `Instant::now()` берётся **до** `connect_tcp`, который резолвит хост сервера: DNS входит в измеряемое время у всех замеров, а не только у первого (комментарий на строке 98 утверждает обратное). |
| `client-core/src/client.rs:245-259` | подписки обновляются последовательно: 25 с таймаут × N, UI «занят». Нужен `JoinSet` + семафор. |

Положительное в клиенте: ping уже параллельный (`JoinSet` + `Semaphore(12)`), тело ответа не скачивается, лог ограничен 1000 строками в памяти без fsync, тело подписки ограничено 8 МБ и пишется потоково.

## 5. Сборка: у сервера нет LTO

`unbihex-client/Cargo.toml:36-39` задаёт `lto = "thin"`, `codegen-units = 1`, `strip`. У `unbihex-server` и `unbihex-engine` **своего `[profile.release]` нет** — серверный бинарник собирается с 16 CGU без LTO. Замер на движке: `lto=fat` + `codegen-units=1` + `panic=abort` дают **+10 % на relay** и −30 % на инициализацию шифра. Для сервера, который стоит на VPS и обслуживает много соединений, это бесплатные проценты:

```toml
# unbihex-server/Cargo.toml
[profile.release]
lto = "fat"
codegen-units = 1
panic = "abort"
```

## 6. Проверено — работает хорошо

- **relay TCP**: один буфер на направление, без промежуточных копий ради логов, `shutdown` на EOF, idle-таймер без busy-loop; с `493aa54` буфер растёт 16→64 КБ на потоковых соединениях. 1132 MB/s на loopback.
- **Никаких глобальных блокировок в data plane**: `ArcSwap` для таблицы маршрутов (`dispatcher.rs:248-250`), per-conn `Mutex<Tcb>` в ipstack, `Semaphore::try_acquire_owned` на handshake в mixed/socks/http.
- **`IpSet`** — бинарный поиск `partition_point`; **geosite/.srs** — succinct-trie, не `Vec`-скан; регэкспы компилируются один раз при загрузке.
- **VLESS/Vision steady state** — прямой passthrough без буферов и копий на чанк; Vision padding ограничен 8 пакетами; nonce AEAD инкрементируется O(1) без аллокаций.
- **TLS-конфиг, `RootCertStore`, provider** строятся один раз на outbound, не на соединение.
- **XHTTP pool** — `parking_lot`, O(#conns), окна h2 как у Chrome, `release_capacity` на чанк, нет busy-loop при нулевой ёмкости.
- **Fake-IP** — LRU O(1) с карантином адресов; **IP-литералы** не проходят через IDNA.
- **HTTP-inbound** — инкрементальный скан заголовка, `MAX_HEAD`, быстрый CONNECT-ответ до апстрим-коннекта.
- **Сокеты** — `TCP_NODELAY` и keepalive на всех исходящих.
- **`TunTcp::poll_shutdown`** — backoff-таймер, не спин.

## 6.1. Правки 1–5 внесены и проверены (2026-10-29)

Внесены пункты 1–4 и 8 из таблицы ниже (окна ipstack, MSS, EOF-спин, буферы сокетов, кеш REALITY). Замеры — на базе `5026c2d` (v0.2.2 + адаптивный буфер ретрансляции), стенд [xray-bench](https://github.com/pshakhmin/xray-bench): старый и новый бинарник по очереди, один и тот же клиент Xray.

| Метрика | До | После | Xray (контроль) |
|---|---|---|---|
| TTFB REALITY-сервера (клиент Xray), RTT≈0 | 6.86 мс | **3.30 мс** | 3.95 мс |
| Соединений/с (тот же стенд) | 255 | **1074** | 448 |

| CPU сервера REALITY, мс/МиБ (на гигабайт; probe — на рукопожатие) | 1.67 | 1.77 | 2.03 |

Тесты: engine 122 (lib, `server`)/101 (по умолчанию) + 13 интеграционных + 2 interop, server 26, client-core 43; `clippy --all-targets` без предупреждений в изменённых файлах; три ветки сливаются в `perf/all` без конфликтов, тесты на слитом дереве зелёные.

**Что важно знать про TUN-правки.** Проверены юнит-тестами (`tcp_config`, EOF-ошибка) и чтением ipstack; TUN-throughput не измерялся: для него нужен хост с живым TUN-устройством. При этом выяснилось ограничение ipstack 1.0.1: окно приёма объявляется 16-битным полем **без window scaling** (`Tcb::get_recv_window`), поэтому 256 КБ `read_buffer_size` не поднимают объявляемое окно выше ~64 КБ. Итог: скачивание (мы — отправитель) получает до 16× (16→256 КБ, лимит `max_unacked_bytes` и окно приложения), а загрузка (мы — получатель) — только до 4× (16→64 КБ, дальше нужен window scaling в ipstack). Чтобы убрать этот потолок, нужен либо патч ipstack, либо свой стек.

**Кеш REALITY** устроен так: ключ — SHA-256 по SNI, флагу TLS 1.3, наборам cipher suites, групп, ALPN и групп key_share, **без GREASE** (0x?a?a браузер шлёт случайно в каждом hello — именно из-за него первый вариант кеша не попадал и TTFB не улучшался). TTL формы 10 мин, адресов `dest` 5 мин, до 8 форм; неудачный probe не кешируется и сбрасывает адреса. Мьютекс не держится во время probe, поэтому упавший `dest` не блокирует остальные рукопожатия. Тест сервера, ожидавший «один probe на рукопожатие», обновлён на «один probe на форму hello».

## Приложение: как воспроизвести замеры

Сквозные замеры (TTFB, throughput, conn/s, CPU) воспроизводятся стендом
[xray-bench](https://github.com/pshakhmin/xray-bench):

```bash
git clone https://github.com/pshakhmin/xray-bench && cd xray-bench
UNBIHEX_REPO=/path/to/unbihex ./setup.sh   # пины версий, ключи, конфиги, dest и приёмник
./bench.sh --quick                         # версии трёх движков + матрица + report.md
```

Микробенчмарки из таблицы (SS AEAD, `check_user`, false sharing, `async_trait`)
выполнялись одноразовым ignored-тестом `unbihex-engine/tests/perf_probe.rs`; в PR он не
входит, чтобы не тащить измерительную обвязку в репозиторий, поэтому эти цифры —
ориентировочные, а не воспроизводимые одной командой.

Ограничения: чисел с живого канала нет; влияние на throughput на реальном RTT выведено из размера окна (`окно / RTT`), а не измерено. Профилировщик (`perf`) не использовался — выводы о доле CPU оценочные и помечены.
