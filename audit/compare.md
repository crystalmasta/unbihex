# Сравнение Unbihex, Xray-core и sing-box: REALITY и XHTTP

- **Дата:** 2026-10-29
- **Версии:** Xray-core `v26.10.29`, sing-box `1.14.4`, Unbihex client `0.2.1` / engine и server `0.1.1` (`27e3905`).
- **Что сравнивается:** поддержка REALITY и XHTTP (матрица) и измеренная производительность на одном стенде (таблицы ниже).
- **Метод:** оба проекта-конкурента — официальные релизы, Unbihex — release-сборка из этого дерева. Один хост (16 ядер, Rust 1.99.1, Go 1.27.3 в сборке Xray), loopback, TLS-«сайт» для REALITY — локальный `openssl s_server` (TLS 1.3, `localhost`), цель — локальный приёмник на публичном (TEST-NET-3) адресе `203.0.113.7`, чтобы маршрутизация всех трёх клиентов не уводила трафик в direct.
- **RTT** эмулировался `tc`/`netem` только на портах туннеля: 0 мс и 50 мс (25+25).
- **Что НЕ измерялось:** TUN-путь Unbihex (нужен хост с `/dev/net/tun`), мобильные клиенты, QUIC/H3, UDP-трафик, реальный WAN.

## 2. Замеры при RTT ≈ 0 (loopback)

Своя пара (клиент ↔ сервер одного проекта), 64 MiB вниз/32 MiB вверх, медиана; CPU — суммарно по процессам за прогон.

| Сценарий | ↓ 1 поток | ↓ 8 потоков | ↑ 1 поток | TTFB (медиана) | conn/s | CPU, мс/МиБ сервер+клиент |
|---|---|---|---|---|---|---|
| Xray, REALITY (TCP) | 372 MB/s | 802 MB/s | 386 MB/s | **3.0 мс** | **544** | 1.9–3.6 + 2.3–2.9 |
| sing-box, REALITY (TCP) | 438 MB/s | **1604 MB/s** | **512 MB/s** | 2.8 мс | 593 | 2.2–2.9 + 1.9–2.7 |
| Unbihex, REALITY (TCP) | 379 MB/s | 990 MB/s | 407 MB/s | 6.1 мс | 281 | 1.7–3.4 + 1.4–3.5 |
| Xray, XHTTP `stream-one` | 147 MB/s | 422 MB/s | 253 MB/s | **0.86 мс** | **3449** | 9–13 + 9 |
| Xray, XHTTP `packet-up` | 146 MB/s | 465 MB/s | **32 MB/s** | 1.0 мс | 3150 | 7.8–13 + 4.5–9.4 |
| Unbihex-клиент → Xray XHTTP | 189 MB/s | 941 MB/s | 289 MB/s | 2.85 мс | 569 | 5.4–7.3 + 4.3–5.3 |

Совместимость (перекрёстные пары, REALITY):

| Пара | ↓ 1 поток | TTFB | conn/s |
|---|---|---|---|
| Xray-клиент → Unbihex-сервер | 372 MB/s | **7.2 мс** | 254 |
| Unbihex-клиент → Xray-сервер | 315 MB/s | 3.7 мс | 557 |
| Unbihex ↔ Unbihex (для сравнения) | 379 MB/s | 6.1 мс | 281 |

**Что видно:**
- По пропускной способности все три близки: 372–438 MB/s на поток, 800–1600 MB/s на 8 потоков. Unbihex не проигрывает по throughput.
- **REALITY-сервер Unbihex добавляет ~4 мс и вдвое снижает темп соединений** (7.2 мс / 254 conn/s против 3.0 мс / 544 у Xray). Разница изолируется перекрёстными парами: клиент Unbihex добавляет ~0.7 мс, сервер — ~4.2 мс. Причина — probe к `dest` на каждое рукопожатие (`inbound/reality.rs:147`) с паузой `gap` 2–15 мс; это ровно находка 2.5 аудита audit5, теперь измеренная.
- **XHTTP резко меняет профиль**: setup в 3.5 раза быстрее (0.86 мс) и в 6 раз выше темп соединений (3449/s), потому что соединения мультиплексируются в готовую h2-сессию, а не поднимают TLS. Цена — в 3–5 раз больше CPU на гигабайт (9–13 мс/МиБ против 2–3.6).
- **`packet-up` убивает аплоад** (32 MB/s против 253 у `stream-one`) — интервал между POST'ами ограничивает один поток. Для интерактива/загрузок `stream-one`/`stream-up` предпочтительнее.
- **XHTTP-клиент Unbihex не получает выигрыша от переиспользования сессии**: TTFB 2.85 мс и 569 conn/s — как у REALITY, а не как у Xray XHTTP (0.86 мс / 3449). Похоже, пул переиспользуется не так, как задумано (`outbound/xhttp/pool.rs`) — требует отдельной проверки.

## 3. Замеры при RTT 50 мс

Один поток вниз, 64 MiB, медиана (для Unbihex — ещё и разброс).

| Сценарий | ↓ 1 поток (RTT 50) | TTFB | Примечание |
|---|---|---|---|
| Xray, REALITY | **89.1 MB/s** | 154 мс | окно TCP растёт, BBR держит канал |
| sing-box, REALITY | **101.5 MB/s** | 154 мс | |
| Unbihex, REALITY (своя пара) | **13–15.6 MB/s** (min 1.4) | 156 мс | |
| Unbihex-клиент → Xray-сервер | **0.92 MB/s** | 153 мс | катастрофа на клиенте |
| Xray-клиент → Unbihex-сервер | 88.8 MB/s | 157 мс | сервер не виноват |
| Xray, XHTTP `stream-one` | 48.6 MB/s | **51 мс** | сессия уже поднята |
| Unbihex-клиент → Xray XHTTP | 69.4 MB/s | **153 мс** | сессия не переиспользуется |
| Unbihex-клиент → Xray, REALITY, **с `tcp_rmem` по умолчанию 4 МиБ** | **108 MB/s** | 153 мс | тот же стенд, изменён только sysctl |

**Разбор.** Падение Unbihex-клиента — не про шифр и не про протокол, а про **окно приёма TCP**. Во время передачи `ss -tinm` показывал у клиентского сокета `rcv_wnd: ~40–55 КБ`, `rcv_space: 38 КБ`, у серверного — `rwnd_limited: 73.8 %`, `notsent: 11 МБ`. Это ровно `окно / RTT`: 50 КБ / 50 мс ≈ 1 МБ/с. Подняв только `net.ipv4.tcp_rmem` (значение по умолчанию 4 МиБ вместо 87 КБ), тот же клиент даёт **108 MB/s** — в 117 раз больше, без единой правки кода. То есть Unbihex-клиент по какой-то причине не даёт ядру увеличить буфер приёма (автотюнинг не срабатывает), тогда как Go-клиенты Xray и sing-box дорастают до нескольких мегабайт сами.

Практический вывод: **на каналах с RTT ≥ 50 мс Unbihex-клиент в proxy-режиме ограничен ~1 МБ/с на поток**, если не поднять `tcp_rmem` в системе. Это важнее, чем 16-КБ окна ipstack для TUN: там хотя бы понятна причина в коде, здесь — системный дефолт, который Unbihex не компенсирует. Лечится явным `SO_RCVBUF`/`SO_SNDBUF` (например, 4 МиБ) на сокетах туннеля в `net/socket.rs` — две строки, обратная совместимость полная.

## 3.1. После правок (те же стенды, старый и новый бинарник по очереди)

Внесены: кеш `DestShape` в REALITY-сервере, буферы сокетов 4 МиБ, окна ipstack 256 КБ, MSS, EOF-спин (см. audit5 §6.1).

| Метрика | Unbihex до | Unbihex после | Xray (контроль) |
|---|---|---|---|
| TTFB REALITY-сервера, RTT≈0 | 6.86 мс | **3.30 мс** | 3.95 мс |
| Соединений/с | 255 | **1074** | 448 |
| Своя пара: ↓ 1 поток, RTT≈0 | 437.5 MB/s | 430.3 MB/s | 360.6 MB/s |
| Клиент → Xray: ↓ 1 поток, RTT 50 мс | 0.85 MB/s | **93.5 MB/s** | 88.6 MB/s |
| Обращений к `dest` на 10 рукопожатий | 10 | 1 | — |

Числа перемерены на базе `5026c2d` (v0.2.2 + адаптивный буфер ретрансляции) стендом [xray-bench](https://github.com/pshakhmin/xray-bench), старый и новый бинарник по очереди. После правок Unbihex-сервер обгоняет Xray по темпу рукопожатий и TTFB, а клиент на RTT 50 мс выходит на уровень Xray. Потолок TUN-режима (16-битное окно ipstack без window scaling, ~64 КБ на приём) этими правками не снимается — нужен патч ipstack.

## 4. Что это значит для REALITY + XHTTP

1. **Сервер ставить Xray.** У Unbihex нет XHTTP-инбаунда, у sing-box нет XHTTP вообще. Unbihex-сервер уместен только как REALITY/TCP-замена Xray (совместимость с панелями и API), но платит +4 мс на рукопожатие из-за probe к `dest`.
2. **Клиент: Xray XHTTP выигрывает на коротких соединениях** (0.86 мс / 3449 conn/s против 3–6 мс / 281–593 у REALITY-клиентов) — это профиль веб-сёрфинга. Но стоит в 3–5 раз больше CPU на гигабайт, а `packet-up` режет аплоад в 8 раз; для скачивания/стриминга лучше `stream-one`.
3. **Unbihex-клиент имеет смысл для REALITY/TCP** (throughput на уровне конкурентов, импорт подписок лучше всех). После правки буферов сокетов RTT 50 мс больше не провал (93 против 89 MB/s у Xray), но переиспользование XHTTP-сессии всё ещё хуже, чем у Xray XHTTP.
4. **Ни одна из трёх реализаций не поддерживает REALITY+XHTTP полностью на обеих сторонах**: Xray — единственная, кто умеет и сервер, и клиент.

## 5. Ограничения

- Loopback + `netem`: абсолютные цифры не переносятся на реальную сеть, сравнимы только между собой. `netem` на `lo` не идеален: при 8 потоках и 50 мс он сам становится узким местом (Xray 23.9 MB/s против 89.1 на одном потоке).
- Конкуренты — Go-бинарники без настройки `sockopt`; Unbihex — со своим планировщиком и rustls. Это сравнение «как есть из коробки», а не «предел возможностей».
- TTFB включает SOCKS-хендшейк, установление туннеля и один round-trip до цели — это то, что чувствует приложение при новом соединении.
- CPU считался по `/proc/<pid>/stat` (utime+stime) для серверного и клиентского процессов, без учёта ядра/прерываний; при spike-нагрузке это занижает счёт.

## Приложение: воспроизведение

```bash
git clone https://github.com/pshakhmin/xray-bench && cd xray-bench
UNBIHEX_REPO=/path/to/unbihex ./setup.sh   # пины версий, ключи, конфиги, dest и приёмник
./bench.sh                                 # версии трёх движков + матрица + report.md
./stand.py run xray_reality 0              # одна клетка отдельно
./stand.py ab xray_reality unbihex_reality 50 --rounds 3   # чередование A/B
```

Конфиги и скрипты стенда — в том же репозитории (`configs/`, `lib/scenarios.json`, `stand.py`, `bench/`). Ключевые условия честности: одинаковая цель (`203.0.113.7:19000`), одинаковый UUID/ключи REALITY, локальный `dest` для REALITY, `finalRules` у freedom в Xray разрешают TEST-NET-цель, у Unbihex — пустые правила маршрутизации.
