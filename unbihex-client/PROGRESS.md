## Этап 0 — Vision + REALITY (готово)
- Ядро: XTLS Vision (`flow=xtls-rprx-vision`), REALITY (pbk / sid / sni), запись-в-запись TLS-поток.
- Проверено против настоящего Xray 26.3.27 (`tests/xray_interop.rs`, запуск с `XRAY_BIN=...`):
  TLS+Vision и REALITY+Vision — TCP, вложенный TLS, UDP, 8 соединений параллельно; неверный ключ даёт ошибку;
  сервер переключается на прямую передачу (splice).
- Клиент: подписки с Vision/REALITY больше не помечаются «не поддерживается».

## Этап 1a — правила и горячая перезагрузка (готово)
- geosite.dat / geoip.dat (v2fly, с `@attr`) — читаются потоково, в память грузятся только нужные категории.
- sing-box `.srs` (rule-set): домены (succinct trie), keyword, regex, IP-подсети, порты, логические правила.
- Горячая перезагрузка: `Instance::reload(config)` меняет маршрутизацию и серверы без разрыва открытых соединений.
- Клиент: режим «Только заблокированные», блок «Базы правил» (скачивание, автообновление раз в неделю),
  смена сервера/настроек на лету без переподключения.

## Этап 1b — UDP, обход DPI, JSON-подписки (готово)
- XUDP (UDP внутри Mux.Cool, как у Xray для Vision) с GlobalID — Full Cone NAT для игр и звонков.
- Фрагментация TLS ClientHello (TLS и REALITY), настройка «Обход DPI» в клиенте.
- Подписки в формате JSON: конфиги Xray (Remnawave, Marzban и т. п.) и sing-box превращаются в серверы.
- Тесты: ядро и клиент зелёные, clippy без замечаний (Linux, Windows, Android).

## Этап 1c — XHTTP (готово)
- packet-up / stream-up / stream-one; HTTP/2 поверх TLS и REALITY с переиспользованием соединений (XMUX),
  HTTP/1.1 без TLS (packet-up). Ссылки `type=xhttp` / `splithttp` с `extra`, XHTTP в JSON-подписках.
- Проверено против Xray: все режимы, UDP, 8 параллельных сессий. HTTP/3 пока нет.

## 25–27.10 — исправления и первый релиз (готово)
- Vision: устранена потеря пробуждения (зависала примерно треть соединений) и блокировка чтения,
  пока занята отдача (скачивание стояло во время загрузки).
- TUN: FIN от сервера доходит до приложения сразу, а не через 60 с с RST; простаивающие TCP-соединения
  живут по лимиту ядра (300 с), а не 60 с; multicast и широковещательный UDP больше не зацикливаются
  через туннель — из-за этой петли режим TUN на Windows не пропускал трафик вообще.
- Клиент: типы пинга (через прокси GET/HEAD, TCP, ICMP), базы правил до 256 МБ с записью на диск,
  новый логотип на всех платформах, автор в метаданных и установщике.
- Первый релиз 0.1.0 на GitHub: установщик и portable-версия для Windows, APK для Android.
- Windows-сборка проверена на живой системе: системный прокси и TUN.

## 27.10 — отпечаток TLS как у Chrome (готово)
- ClientHello Chrome для TLS и REALITY: GREASE, набор шифров и расширений Chrome, перемешивание расширений
  на каждое соединение, GREASE ECH, ALPS, сжатие сертификатов brotli. JA4: `t13d1516h2_8daaf6152771_d8a2da3f94cd`
  (проверено сервисом tls.peet.ws), до этого — `t13d1011_…` rustls.
- Пост-квантовый обмен ключами X25519MLKEM768 на чистом Rust (`ml-kem`), отдельная доля X25519 как у Chrome.
- rustls 0.23.46 вендорен в `unbihex-engine/vendor/rustls` с одним хуком (`UNBIHEX-PATCH.md`): ClientHello
  переписывается до хеширования, так что транскрипт рукопожатия сходится с сервером.
- Параметр `fp` ссылок и JSON-подписок: любой браузер пока даёт Chrome, `none` — ClientHello rustls.
- Проверено на 15 живых серверах (14 TLS+Vision, 1 REALITY+Vision): все подключаются.
- Исправлена потеря пробуждения в TLS-потоке: чтение больше не отправляет данные само, из-за этого
  при передаче больших объёмов в два направления соединение могло зависнуть.

## 29.10 — чистый туннель для роутеров и серверов
- Ядро: `route.default_interface` и `route.default_mark` (`SO_MARK`, только Linux) для всех исходящих сокетов, как в sing-box.
- Клиент: настройка «TUN без маршрутов» (`tun_routes`), имя TUN, интерфейс и метка; без маршрутов клиент
  не трогает ни маршруты, ни DNS системы.
- `unbihex-cli`: `connect --no-routes / --tun-name / --interface / --mark`, `settings`,
  `run -c` и `check -c` для конфига ядра без подписок (SIGHUP перечитывает файл).

## 29.10 — клиент 0.2.2: правила с AdGuard и DoH, Windows
- Ядро: sniffing в TUN. Имя из TLS SNI или HTTP `Host` для соединений к настоящим IP, только для правил,
  подключение идёт к исходному IP. Раньше с AdGuard, антивирусом или DoH в браузере доменные правила не срабатывали:
  в режимах «Только выбранные» и «Только заблокированные» сайты уходили напрямую (issue #2).
- Windows: кнопка «Разрешить прокси приложениям из Microsoft Store» (исключения loopback через API брандмауэра,
  отмена снимает только свои). Предупреждение в журнале, если после подключения Windows шлёт трафик мимо TUN.
- Окно, закрытое в трей, уничтожается вместе с WebView2: в фоне ~6 МБ вместо ~210 МБ.
- Подписки-JSON: серверы балансировщика (`routing.balancers`, селекторы-префиксы) все попадают в список,
  а не только `proxy`.
- Базы правил: обрыв скачивания (на телефоне, issue #4) больше не губит загрузку. До 4 попыток с докачкой
  через `Range`, в ошибке видна настоящая причина.

## 29.10 — нагрузочный тест
- Буфер ретрансляции растёт с 16 до 64 КБ, когда идёт поток данных: путь без шифрования 6,8 → 13,1 Гбит/с на один
  поток и 31 → 60 Гбит/с на восемь, CPU тот же; молчащие соединения остаются на 16 КБ.
- Чтение TLS по одной записи оказалось не узким местом: TLS-слой отдельно держит ~10 Гбит/с на поток. Крупное
  чтение сокета его не ускорило, правка откачена; остались тесты перехода Vision и нарезки записей
  и замер `tls_throughput`. Один поток REALITY на этой машине то ~2,5, то ~5 Гбит/с (планирование потоков).

## 29.10 — клиент 0.2.3, ядро 0.1.3: скорость на длинных плечах
- TUN: окна userspace-стека 16 → 256 КБ и MSS `mtu − 60` вместо 536 Б; пропавшее TUN-устройство больше не
  крутит ядро процессора на 100 %.
- Сокеты туннеля: `TCP_NODELAY` и буферы 4 МиБ (`SO_RCVBUF`/`SO_SNDBUF`) на исходящих и принятых соединениях.
- Автор этих правок — Павел Шахмин (github.com/pshakhmin), PR #18.

## 30.10 — меню на весь экран в unbihex-cli
- `unbihex-cli` без команды в терминале (или `unbihex-cli tui`) открывает меню на ratatui, как у btop: серверы
  с пингом (обновляется по мере ответов), подключение и переключение на лету, режим и маршрутизация с клавиатуры,
  графики скорости, трафик через VPN и напрямую, журнал (логи ядра идут в него, а не на экран).
- Добавление ссылок и подписок во всплывающей строке, вставка из буфера обмена работает и по SSH.
- TUN по SSH: первое нажатие Enter только предупреждает, что сессия может оборваться.
- Две сборки консольного клиента: `unbihex-cli` без меню (роутеры, NAS, скрипты) и `unbihex-cli-tui` с меню (фича `tui`).

## 31.10 — клиент 0.2.4, ядро 0.1.4
- Android: VPN не отключается, если смахнуть приложение из недавних. Раньше вместе с окном завершался весь
  процесс, а с ним ядро; теперь, пока VPN включён, процесс остаётся, а окно создаётся заново при открытии.
- Android: уведомление «VPN включён» с кнопкой «Отключить»; VPN-служба работает на переднем плане, и система не
  закрывает её в фоне. Отключается в настройках («Прочее»), по умолчанию включено.
- Android: имена серверов и direct-сайтов резолвятся системным DNS, 1.1.1.1 / 8.8.8.8 — запасные (issue #14:
  в сетях, где они недоступны, туннель не запускался).
- Ядро: DNS опрашивает серверы параллельно со сдвигом и повторяет потерянный запрос; первым идёт ответивший.
- Ядро: свой ipstack (`vendor/ipstack`): масштабирование окна TCP, переотправка по таймеру, ограниченная очередь,
  ожидание вместо потери пакетов при полной очереди TUN, копирование одного сегмента. 64 параллельных скачивания
  через TUN раньше зависали навсегда, теперь проходят; закрытие соединения больше не блокирует потоки tokio.
- Linux / Android: буфер сокета 4 МиБ ставится, только если `rmem_max`/`wmem_max` его допускают; иначе ядро ОС
  подбирает размер само.
